Roles with access

  • All roles — this is the only pre-authentication screen. Owner/Admin/Manager get an additional mandatory 2FA step after credentials succeed (PRD §3.1).

Data loaded on entry

  • State A: none (public route).
  • State B: GET /staff?active=true scoped to the terminal's configured restaurantId, to populate the staff picker avatars/names.

Every button's action + destination

  • Login Method toggle — switches between State A and State B in place, no navigation.
  • "Log In" (State A) — POST /auth/login with email/password → on success, sets httpOnly JWT cookies (15 min access / 7 day refresh) and routes to the role-based landing screen (see sitemap §2). Owner/Admin/Manager see a 2FA prompt first.
  • Staff tile (State B) — selects staff for PIN entry, no navigation.
  • Keypad (State B) — fills PIN dots; "Log In" — POST /auth/pin-login → same routing as State A. Intended for shared POS terminal clock-in, not a full session replacement for back-office roles.
  • "Forgot password?" — no self-service flow in MVP (PRD only specifies admin-forced reset on first login); link shown for completeness, destination is "contact your admin" messaging, not a reset-email flow.

Empty state

  • State B with zero staff configured yet (fresh install, before Owner completes onboarding) — staff picker shows: "No staff accounts yet. Log in with your admin email and password to get started."

Error states

  • Invalid credentials: "Incorrect email or password. Try again." (shown above, inline above the form).
  • Deactivated account: "This account has been deactivated. Contact your admin."
  • Incorrect PIN: "Incorrect PIN. Try again." — after 5 failed attempts, PIN entry locks for that staff tile for 60 seconds (mirrors password-login lockout policy for brute-force protection).
