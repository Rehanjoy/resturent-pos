4. Key user journeys (step by step)

Journey A — Full order lifecycle: New Order → Send to Kitchen → KDS → Serve → Settle Bill

Table Grid: tap a Free table
→
New Order opens, table pre-selected
→
Browse category tabs, tap dishes → "Add to Billing"
→
Customize (spice/add-ons), qty stepper in Bills rail
→
"Send to Kitchen" → KOT created, status Draft→Sent
→
KDS: ticket appears in Sent column, elapsed timer starts
→
Chef: "Mark Item Ready" / "Mark All Ready" → status In-Kitchen→Ready
→
Server/Cashier: "Mark Served" from New Order/Table view → status Served, ticket clears from KDS
→
Settle Bill: itemized review, discount, payment mode
→
"Settle Bill" → invoice generated, status Billed→Closed
→
Table Grid: table auto-freed to "Needs Cleaning"

6. Open questions / judgment calls for the client to confirm

  • Server's landing screen: defaulted to Table & Area Grid (no Dashboard access). Confirm this is preferred over landing directly on New Order / an empty table-selection prompt.
  • Chef's landing screen: defaulted to Kitchen Display. Confirm — alternative is a simple "today's assigned tickets" view if KDS ever gets multi-station routing (Phase 2).
  • Dashboard's "Weekly sales trend" and "Low-stock alerts" widgets are listed in PRD §3.2 but not in the brief's scoped MVP bullet for Dashboard. Low-stock alerts specifically depends on the Inventory module (Phase 2) — excluded from the MVP dashboard wireframe. Weekly trend graph doesn't depend on Inventory — included as an optional card, flagged for confirm.
  • Settings screen (PRD §3.14 — restaurant profile, tax config, discount policy) is referenced by nav rail but was not requested in this wireframing round and so is not wireframed; shown disabled/grayed in the nav on every screen. Needs its own pass before coding starts, since tax config directly feeds Settle Bill's tax breakdown.
  • Server's Table CRUD scope: RBAC matrix lists Server as "Create/Edit" for Tables. Interpreted narrowly as seating/status actions (seat guest, mark needs-cleaning) — not structural table CRUD (add/rename/change capacity/area), which stays Owner/Manager only in the wireframe. Confirm this split.
  • Reports "sales only" scope for Cashier: interpreted as Sales Overview + Revenue by Category + Revenue by Payment Mode + Top Dishes, excluding only the Staff Performance tab (personnel data). Confirm this boundary.
  • Discount placement: discount entry, with manager-approval lock, is modeled as living on the Settle Bill screen only (matches PRD §3.10). The New Order right-hand "Bills" rail still shows a Subtotal/Tax/Total breakdown and a payment-mode pre-select per the client's reference screenshot, but the Discount field there is informational/carried-forward, not where discounts are actually applied. Confirm this matches intent, since the reference screenshot shows a full Discount row on the New Order rail too.
  • KDS "Ready" ticket clearing: per PRD §3.4, tickets auto-clear from the KDS queue only when "Serve" is actioned from the POS/Table view, not from a button on KDS itself. Confirmed as designed this way in the wireframe — flagging in case the client actually wants a KDS-side "Served" button too for kitchens without a POS terminal nearby.
